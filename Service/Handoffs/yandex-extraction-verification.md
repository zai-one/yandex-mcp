## 1. Что просили и что сделано

Yandex 0.1.0 — самостоятельный Git/MCP-проект с реальными адаптерами Direct,
Метрики, Search/Wordstat и Webmaster, всеми 44 исходными инструментами,
stdio/Streamable HTTP, тестами, версией, lock, wheel/sdist, документацией,
лицензионными уведомлениями upstream и source provenance. Самостоятельный
сервер не импортирует AI Kit или mcp_platform. SQLite сохраняет account/actor,
admission, аудит, approvals, budgets, write ledger и Search jobs. Отдельный
worker выполняет платный POST с durable dispatch intent и восстанавливает
polling по сохранённому operation ID. Неизвестный исход не повторяется вслепую.

Один точный wheel подключён в два собственных gateway-кандидата на исходных
разных базах. Основной кандидат переносит 17 core tools, Webmaster — 27.
FastMCP 3.4.4/4.0.0 соответственно сохранены. Ветки не объединялись.
Gateway сохраняет центральную авторизацию, scopes, admission/retries, quotas,
approvals, audit и владельца jobs/write state. Самостоятельный StateStore или
worker внутри платформы не создаётся. Контракт клиента и URL не меняются.

Исправлены два воспроизведённых дефекта нового выделения: повторная проверка
бюджета перед отложенным платным dispatch и потеря центрального cooldown при
вложенном вызове legacy WebmasterActions. Независимые полные ответы ниже.
Дополнительно закреплены LF в .gitattributes; исходный runtime SHA, созданный
до этого файла, воспроизводится checkout с core.autocrlf=false. Первый clone
build с глобальной Windows-настройкой CRLF сохранён как FAIL хеша, хотя его
тесты прошли. После канонического checkout байты wheel совпадают с manifest.

## 4. Что может сломаться

- Общий endpoint и контракт сохранены локально, но production состояние не
  проверялось. Разные source branches остаются разными release-кандидатами.
- Standalone replicas одного account должны пользоваться одним защищённым
  SQLite. Разные файлы разделят лимиты. Local stdio/approval CLI — доверенный
  операторский доступ; MCP клиент не должен иметь доступ к shell/state.
- После uncertain POST резерв и pending/unknown state сохраняются. Оператор
  сначала сверяет upstream; новый key или rollback не разрешает повтор.
- Для standalone Search нужен отдельный worker с тем же account/config/state.
  Gateway использует свой worker и свои записи, без второго state owner.
- `completed` Search означает полученный терминальный результат операции;
  upstream error сохраняется в raw_provenance.error, а не становится успехом.
- Wheel привязан к каноническим Git blobs/LF. Для runtime SHA до .gitattributes
  clean build использует core.autocrlf=false; будущие checkout получают LF
  из .gitattributes. Evidence/doc commits не меняют закреплённый release wheel.
- Rollback возвращает прежний gateway build, сохраняя центральные ledgers и
  jobs. Перед переключением учитываются in-flight и uncertain операции.

## 5. Вопросы скептику

- Атомарны ли approval consume, бюджет и очередь при гонках/повторах?
- Есть ли повтор платного POST после crash, timeout или потери lease?
- Сохраняется ли бюджет при переносе dispatch между месяцами/смене лимита?
- Видит ли central governor нужный класс ошибки до внешнего error envelope?
- Сохраняются ли retry admission и единый владелец durable state в gateway?

Критерий: реальный самостоятельный MCP, неизменные исходные контракты,
отсутствие конкретных новых P1/P2 в auth, paid/write state и gateway policy.

## 6. Скептик

Агенты `/root/yandex_state_skeptic` и `/root/roistat_skeptic`, независимый review
предоставленных исходников. Инструменты, память, файлы и сеть запрещены;
это не независимый запуск и не подтверждение live behavior. Четыре ответа
вклеены ниже полностью, включая предварительные сомнения и P2:

**Строгий вердикт: чисто в пределах предоставленных исходников. Безусловно доказуемых P1/P2 не установлено.** Инструменты, файлы, память и сеть не использовал; заявленные 128 тестов самостоятельно не проверял.

Атомарное admission выглядит корректным: проверка approval, резервирование бюджета, потребление approval и создание job находятся в одном `BEGIN IMMEDIATE`. Ошибка откатывает всю транзакцию. Совпадающий повтор возвращает существующую job до нового резервирования; несовпадающий запрос отвергается. Уникальные ограничения дополнительно закрывают конкурентное использование approval и ключа.

Для показанного crash recovery повторный платный POST не обнаружен: `dispatch_intent` сохраняется до вызова submit; просроченная job с `stage='dispatching'` становится `failed/submission_outcome_unknown`, а не возвращается в очередь. Проверки owner и lease не позволяют старому worker записать результат после потери владения.

Есть два конкретных **условных контрпримера**, которые нельзя объявить подтверждёнными без отсутствующих деталей:

1. **Потенциальный P1: `ProviderRateLimited` после фактической отправки POST.**  
   Вход: платный POST уже допущен и отправлен, затем `runtime.call` поднимает `ProviderRateLimited`, не являющийся `ProviderAdmissionDenied`. Внешний обработчик без проверки `admitted_count` сохраняет `stage='queued'`; следующий worker может выполнить второй POST по той же approval. Переход состояния доказуем из фрагмента, но возможность такого исключения после отправки — нет: преобразование HTTP-ответов в исключения не предоставлено.  
   **Уверенность:** высокая в условном переходе, недостаточная для UPHELD достижимости.  
   **Цена ошибочной правки:** запрет безопасного повтора после заведомо отклонённого провайдером запроса; потеря доступности и сохранение резерва бюджета. Для окончательного вердикта нужен путь обработки HTTP 429 и иных источников `ProviderRateLimited`.

2. **Потенциальный P2: завершившаяся операция с ошибкой получает `completed`.**  
   Вход: polling возвращает `done=True` вместе с ошибкой операции, а `split_operation(response)` возвращает нормализованный результат. Worker безусловно сохраняет `completed`. Если этот статус означает успешное выполнение, клиент получает ложный успех. Однако полного `split_operation` и контракта статуса `completed` нет: функция может отвергать ошибочный ответ, а статус может обозначать только завершённость.  
   **Уверенность:** высокая в условном переходе, недостаточная для UPHELD поведения целиком.  
   **Цена ошибочной правки:** неверная классификация допустимого результата либо изменение контракта клиентов. Для окончательного вердикта нужны обработка ошибки в `split_operation` и значение `completed` в публичном контракте.

Эти два пункта — пределы доказательства, **не подтверждённые дефекты**. Они также не позволяют распространить вывод «чисто» на весь HTTP adapter и публичную семантику результатов.


**Вердикт: чисто в границах предоставленного изменения. Доказуемых новых P1/P2 не найдено.** Проверка выполнена только по переданному коду; тестовые логи самостоятельно не проверял.

Новая `dispatch_intent` сохраняет необходимые гарантии:

- Проверка актуальных лимитов, перенос резерва между месяцами и установка `stage='dispatching'` выполняются в одной транзакции `BEGIN IMMEDIATE`. Конкурентный worker не может проверить бюджет между этими действиями. Ошибка, включая потерю lease на последнем UPDATE, откатывает перенос резерва.
- Двойного учёта нет: резерв текущего месяца уже входит в `total/own`, поэтому `extra=0`; резерв прошлого месяца ещё не входит, поэтому прибавляется ровно `amount`. Перенос выполняется обновлением существующей строки.
- Смешения actors не обнаружено: `own` считается для actor связанной approval; admission ранее связал approval, job и резерв с одним principal. Общий `total` включает всех actors аккаунта.
- `BudgetDenied` возникает до успешного `dispatch_intent` и до POST. Worker сохраняет наблюдаемое состояние `waiting`, `error_code='budget_denied'`, `stage='queued'`. Это явный отложенный отказ, а не проглатывание ошибки. Повторная проверка через 60 секунд не потребляет новую approval и не создаёт дополнительный резерв.
- После успешного `dispatch_intent` сохраняется прежняя защита от повторного POST при неизвестном исходе: просроченный `dispatching` переводится в `submission_outcome_unknown`.

Два условных пункта первого ревью закрываю:

1. **Повтор после `ProviderRateLimited` — REFUTED при предоставленном транспортном контракте.** Единственные источники — отказ admission до socket и явный HTTP 429, для которого контракт разрешает повтор. POST с timeout, transport error или 5xx не попадает в эту ветку и сохраняет неизвестный исход. Запрет повтора на основании одного лишь `admitted_count>0` ошибочно убрал бы разрешённое восстановление после 429.

2. **`done+error → completed` — REFUTED при предоставленном публичном контракте.** `completed` означает получение терминального результата операции; ошибка сохраняется в `raw_provenance.error`. Это не заявление об успешности upstream-операции. Переклассификация такого ответа в `failed` изменила бы существующий контракт.

**Уверенность высокая для рассмотренных переходов состояния и SQL-атомарности.** Вывод опирается на заявленные инварианты защищённого хранилища, разрешённого повтора после HTTP 429 и значения статуса `completed`. Он не является независимым подтверждением тестов или live-поведения провайдера.


Обнаружил конкретный разрыв типов в **legacy `mcp_platform.webmaster_actions.WebmasterActions`**, но для подтверждения P2 нужен обработчик ошибок центрального `registry.call`.

Из представленного кода следует такой путь:

1. Legacy actions обёрнут через `install_methods` → общий `_depth` становится больше нуля.
2. Actions вызывает `RegistryFacade.call` → центральный `registry.call` → обёрнутый адаптер.
3. `TransportBridge` переводит ошибку HTTP из `base` в `service`.
4. Адаптер видит `previous > 0` и оставляет ошибку типа `service`.
5. **Центральный `registry.call` получает пакетное исключение вместо платформенного.** Его обработчики `except base.ProviderRateLimited` или `except base.ProviderError`, если они есть, будут пропущены. Последующий перевод на внешней границе actions этого не исправляет.

Для MCP-пути с необёрнутым пакетным `WebmasterActions` этот конкретный механизм не воспроизводится. Смешение возникает из-за общего счётчика глубины для actions и адаптеров, между которыми расположен центральный registry.

Передай текст `registry.call` и вызываемого им governor-кода с обработкой исключений: это позволит установить последствие, например пропуск cooldown, и подтвердить либо снять P2. Исправление при подтверждении — ограничить подавление перевода вложенными вызовами адаптера, исключив внешний actions-слой.

По остальным представленным связям — callback context, Wordstat refund, фабрики записей и принадлежность store/jobs — конкретных P1/P2 пока не обнаружил. Инструменты не использовал, тесты не запускал; их результаты остаются свидетельством автора.


**UPHELD — исходная находка подтверждена, P2.** Общий `_depth` для Actions и адаптера позволял пакетному `ProviderRateLimited` пройти мимо платформенного обработчика governor. В результате cooldown не сохранялся, и следующий запрос повторно обращался к провайдеру. Аналогичный разрыв затрагивал регистрацию перечисленных transient-ошибок.

**Исправление корректно по представленному коду.** Отдельный `yandex_actions_depth` сохраняет обработку вложенных методов Actions, а адаптер переводит исключение в платформенный тип до возвращения в governor. Затем `RegistryFacade` восстанавливает пакетный тип для внутренних обработчиков Actions. Восстановление обоих callback-контекстов через `finally` сохранено.

Авторский регрессионный тест проверяет существенное последствие: первый запрос устанавливает cooldown, второй отклоняется без дополнительного HTTP-вызова. Параметризация охватывает legacy и MCP-пути, дополнительно проверяет внешние типы исключений и очистку контекстов. Сообщённые результаты: до исправления — `1 failed, 1 passed`, после — `2 passed`.

**Оставшихся конкретных P1/P2 в представленном материале не обнаружил.** Инструменты, память, файлы и сеть не использовал; тесты самостоятельно не запускал и логи не читал. Вывод ограничен приложенными фрагментами и описанием авторского воспроизведения; итог полных gates здесь не подтверждён.


**Реакция на находки:** исходный P2 legacy cooldown подтверждён падающим
тестом и исправлен в Webmaster gateway `886c0b5`; раздельные depth-контексты
общего bridge присутствуют также в core `6b3ee24`. Повторный review подтвердил
исправление. Два условных замечания по 429 и `completed` сняты скептиком после
предоставления transport и исходного status contract; ответы сохранены целиком.
Исправление отложенного бюджета входит в service `a500b0e`, проверено state
скептиком и тестами. Конкретных оставшихся P1/P2 в представленном review нет;
его пределы не заменяют проверки контейнера, CI и production.
